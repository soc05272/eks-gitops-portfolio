# 발표자료 구성안 — EKS GitOps Portfolio

> 가정: 발표 10~12분 + Q&A. 슬라이드 14장.
> 관통 메시지: **"운영하던 사람이 클라우드로 넘어와, 만들고 → 검증하고 → 회수까지 해봤다"**
> 각 장의 "한 줄"이 그 슬라이드에서 청중이 기억해야 할 문장이다.

---

## 1. 표지

- 제목: 온프레미스 솔루션 운영 경험의 클라우드 네이티브 전환
- 부제: EKS + GitOps + 관측성 — 구축부터 회수까지
- 이름 / GitHub repo 주소(QR 추천)

## 2. 전환 동기 (경력 연결)

- **한 줄**: "운영하며 겪은 세 가지 한계를 직접 해결해보려고 시작했다"
- 솔루션 엔지니어 경력: Docker · PostgreSQL · 모니터링 운영
- 한계 3가지: ① 수동 배포 ② 환경 재구축의 어려움 ③ 수동 장애 대응
- (이 3가지가 뒤에서 GitOps / IaC / 관측성으로 각각 해소됨을 예고)

## 3. 프로젝트 한 장 요약

- **한 줄**: "3주간 78개 리소스, 트러블슈팅 6건, 전 기능 실증 3회"
- 표: 목표 / 기간(실작업 7일) / 핵심 기술 / 규모
- 결과 스냅샷: E2E ✅ · GitOps 자동 배포 ✅ · Slack 알람 ✅ · 수명주기 재현 3회 ✅

## 4. 아키텍처 전체도

- **한 줄**: "사람의 개입은 git push 하나"
- README의 다이어그램을 시각화 (배포 파이프라인 / VPC 3계층 / 트래픽 경로)
- 포인트 3개만 짚기: OIDC 키리스 인증 · IRSA 권한 분리 · 3계층 서브넷

## 5. 의사결정 (ADR)

- **한 줄**: "기술 선택마다 트레이드오프를 기록했다"
- 3건 요약: ArgoCD(pull, drift 감지) vs CI 직접 배포 / RDS vs 클러스터 내 DB /
  단일 NAT vs AZ별 NAT
- "과하지 않게" 원칙 — 서비스 메시·멀티클러스터를 뺀 이유도 한 줄

## 6. 애플리케이션 (짧게)

- **한 줄**: "앱은 인프라 전체를 관통하며 검증하는 최소 단위"
- POST /summaries 한 요청의 경로: 인터넷→ALB→파드→(NAT)→Claude API→RDS
- stateless / Secret 주입 / 프로브 계약 — 클라우드 네이티브 규약 준수
- (상세 로직 질문 대비: docs/app-logic.md)

## 7. GitOps 파이프라인

- **한 줄**: "push부터 배포까지 자동, 롤백은 git revert 한 번"
- 흐름도: push → Actions(OIDC) → ECR → 매니페스트 repo 자동 커밋 → ArgoCD → 롤링
- 실증: v0.2.1 배포 — 인터넷에서 version 필드 전환 확인
- repo 분리(앱 공개/매니페스트 비공개) 이유 한 줄

## 8. 관측성

- **한 줄**: "수동 장애 대응을 선제 감지로 바꿨다"
- 경로: Prometheus → Alertmanager → Slack (+ RDS 지표는 cloudwatch-exporter로 단일화)
- **Slack 알람 실수신 스크린샷** (FIRING → RESOLVED 사이클)
- 파드를 직접 죽여서 검증했다는 점 강조

## 9. 트러블슈팅 ① — EKS 노드그룹 CREATE_FAILED

- **한 줄**: "조용한 실패는 원인이 적히는 곳을 찾아야 한다"
- 38분 무증상 실패 → health.issues는 비어 있었다 → ASG 활동 로그에서 원인 발견
- Free Plan 인스턴스 제약 → 우회 대신 근본 해결(Paid 전환), 코드 무수정 재성공

## 10. 트러블슈팅 ② — GitHub Actions OIDC 인증 실패

- **한 줄**: "추측 대신 상대가 실제 보낸 값을 봤다 (CloudTrail)"
- 에러는 한 줄뿐 → 가설 2회 기각 → CloudTrail userIdentity에서 실제 sub 확인
- GitHub sub 신형식(@계정ID/@저장소ID) vs 모듈의 구형식 — ID까지 고정해 해결, 보안 강화 부수효과

## 11. 트러블슈팅 ③ — 같은 사고의 재발과 절차 개선

- **한 줄**: "두 번째 재발은 '조심'이 아니라 절차를 바꾸라는 신호"
- PAT 등록 사고: 1차(개행) → pbpaste 도입 → 2차(클립보드 덮어쓰기) → hidden prompt로 교체
- 실수를 개인 부주의가 아닌 프로세스 문제로 다루는 태도 어필

## 12. 실증 결과 — 전체 수명주기 리허설

- **한 줄**: "코드와 문서만으로 재현 → 검증 → 회수, 하루에 완주"
- 재기동 8단계 루틴(3회 실증) → 전 기능 재검증 → 종료 4단계 → 잔여물 0 · 과금 $0
- 비용 운영: 상시 월 $164 → destroy 병행으로 리허설 하루 2천 원 미만

## 13. 배운 점 & 다음 단계

- **한 줄**: "운영 경험이 클라우드에서 어떻게 확장되는지 체감했다"
- 배운 점 3개: 계층별 완료 기준 구분(rollout≠LB 무중단) / 실패는 기록될 곳에서 찾기 /
