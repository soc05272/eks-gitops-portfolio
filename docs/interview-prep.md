## 1. 전환 동기·경력 연결

**Q. 왜 클라우드/DevOps로 전환하려고 하나?**
- **"운영하던 대상을 직접 설계·구축해보고 싶었다"** — 모니터링·장애 대응을 하다 보니 "이 시스템이 왜 이렇게 설계됐는지"가 궁금해졌고, 직접 세워보니 운영 경험이 설계 판단(SG 참조 방식, 프로브 설계, 알람 경로 단일화)에 그대로 쓰였다
- 온프레미스 경험이 감가상각이 아니라 **자산**임을 프로젝트로 증명: PostgreSQL 운영 경험 → RDS 선택 근거(ADR-002), 모니터링 경험 → 관측성 스택 설계

**Q. 온프레미스와 클라우드 운영의 가장 큰 차이는?**
- **"자원이 소모품이 된다"** — 온프레미스에서 서버는 아끼는 대상이었지만, 클라우드에선 destroy/apply를 반복하는 게 오히려 검증 수단. 스냅샷·IaC 덕에 "다시 만들 수 있는가"가 "고칠 수 있는가"보다 중요해진다
- 비용이 설계 변수가 된다 — 단일 NAT, Spot, destroy 병행 같은 결정이 전부 비용에서 출발

## 2. 아키텍처·설계 질문

**Q. 왜 EKS인가? (ECS나 EC2도 있는데)**
- 규모만 보면 과한 선택임을 **인지하고** 골랐다 — 쿠버네티스가 컨테이너 오케스트레이션의 실무 표준이고, 학습 가치와 이직 시장 수요를 우선했다. 대가(컨트롤플레인 월 $73)는 destroy 운영으로 통제

**Q. ArgoCD를 쓴 이유? CI에서 kubectl apply 하면 안 되나?**
- 된다. 하지만 push 방식은 **클러스터 자격증명이 CI로 나가야 하고**, 배포된 상태와 Git이 어긋나도 모른다
- ArgoCD(pull)는 자격증명이 클러스터 안에 머물고, **drift를 감지해 Git 상태로 자동 복원** — "지금 뭐가 배포돼 있는지 아무도 모르는" 온프레미스 시절 문제를 구조적으로 해결
- 롤백 = 매니페스트 repo `git revert` 한 번

**Q. DB를 왜 클러스터 안에 안 넣고 RDS로 뺐나?**
- **"쿠버네티스는 죽어도 되는 것을 굴리는 플랫폼"** — Spot 노드까지 쓰는 클러스터에 데이터를 두는 건 상성이 나쁘다
- StatefulSet+PV로 가능은 하지만 백업·페일오버·패치가 전부 숙제로 남는다. 관리형에 위임하고 앱과 DB의 수명주기를 분리하는 게 표준 패턴
- 반론 대비: k8s에 DB를 두는 경우도 있다(관리형이 없는 특수 DB, 대규모 멀티테넌트 + 전담 플랫폼팀)

**Q. PostgreSQL 버전은 왜 17인가? 메이저 버전 업그레이드는 어떻게 하나?**
- 17 선택 이유: **현업에서 운영 중인 솔루션의 DB가 PostgreSQL 17** — 운영하던 버전 그대로 클라우드에서 다뤄 경력 연속성을 유지. RDS 서울 리전의 17.x 지원과 db.t3.micro 조합 가능 여부를 CLI로 확인하고 결정
- 이 프로젝트에서는 destroy/apply 재생성 구조라 **코드 한 줄 변경**으로 끝 — "업그레이드"가 아니라 처음부터 17로 태어난다
- **프로덕션이라면 얘기가 다르다** — 데이터가 있는 DB의 메이저 업그레이드는: `allow_major_version_upgrade` + 다운타임 감수, 또는 **Blue/Green 배포**(17 복제본을 만들어 검증 후 전환). extension 호환성 확인, 업그레이드 후 통계 재수집(`ANALYZE`), 사전 리허설까지가 세트
- **"stateless는 재생성, stateful은 업그레이드 경로 설계"** — 상태 유무가 변경 전략을 가른다는 프레임으로 답하면 좋다

**Q. IRSA가 뭔가? 왜 썼나?**
- IAM Roles for Service Accounts — **파드(ServiceAccount) 단위로 IAM Role을 부여**하는 방식
- 노드 Role에 권한을 얹으면 그 노드의 모든 파드가 권한을 물려받는다. ALB 생성 권한은 컨트롤러 파드에게만 필요하므로 EKS OIDC provider를 신뢰하는 전용 Role을 SA에 바인딩 — 최소 권한 원칙
- 이 프로젝트에서 4종 운영 (ALB Controller / EBS CSI / cloudwatch-exporter / GHA용은 별도 OIDC)

**Q. GitHub Actions 인증은 어떻게 했나? 액세스 키를 저장했나?**
- 안 했다. **OIDC 키리스 인증** — GitHub이 발급하는 단기 토큰을 AWS Role이 신뢰 정책(sub 조건)으로 검증
- 장점: 장기 자격증명이 어디에도 저장되지 않고, repo·브랜치 단위로 권한을 좁힐 수 있다
- 이 신뢰 정책의 sub 형식 문제로 겪은 트러블슈팅이 §5-2

**Q. K8s Secret은 안전한가?**
- **"base64는 인코딩이지 암호화가 아니다"** — 권한 있는 사람은 복원 가능
- 이 프로젝트의 목적은 "비밀값이 코드·이미지·repo에 남지 않게 격리"이고 그 조건은 충족. 더 강한 요구(자동 순환, 감사)면 Secrets Manager + External Secrets로 확장 — 규모 대비 과잉이라 백로그

**Q. 단일 NAT는 SPOF 아닌가?**
- 맞다, **알고 수용했다** — AZ별 NAT 대비 월 $40 절감, NAT 장애 시 영향은 아웃바운드뿐(인바운드 서비스는 유지). 프로덕션 기준은 AZ별 배치임을 ADR-003에 명시

## 3. 쿠버네티스·인프라 개념 질문

**Q. 앱을 stateless로 만든 이유?**
- 파드는 언제든 죽고 다시 태어난다(배포, Spot 회수, 노드 장애). 상태를 파드에 두면 레플리카 2개가 서로 다른 데이터를 갖게 된다 → **상태는 전부 RDS로, 파드는 소모품으로**

**Q. liveness/readiness 프로브의 차이와 설계?**
- liveness 실패 = 재시작, readiness 실패 = 트래픽 제외
- `/healthz` 하나로 계약. **앱 시작 시 DB 연결·테이블 생성이 성공해야 뜨도록** 설계해서 "Ready = RDS 연결까지 정상"이라는 검증이 공짜로 따라온다

**Q. 배포했는데 무중단이 아니었다면 어디를 보나?**
- 실제로 겪었다 — rollout은 성공인데 ALB 응답이 1회 실패
- **완료의 기준이 계층마다 다르다**: rollout 성공은 쿠버네티스 내부 기준, ALB의 타깃 전환(draining/헬스체크)은 비동기
- 해법: Pod Readiness Gate(ALB healthy가 readiness 조건에 주입) + preStop sleep

**Q. HPA와 Cluster Autoscaler의 차이는?**
- **"HPA는 파드를, CA는 노드를 늘린다"** — HPA는 CPU 사용률(분모=requests) 기준으로 레플리카 수를 조절하고, 노드가 꽉 차 파드가 Pending이 되면 그때 CA가 노드를 추가한다. 계층이 다르고 담당 도구가 다르다
- 이 프로젝트는 HPA(2~6, CPU 50%)를 매니페스트에 반영. 전제 조건인 **metrics-server가 EKS에 기본 미설치**라는 함정, 축소는 5분 안정화 창 이후라는 특성까지 문서화
- 꼬리질문 대비: 우리 앱은 Claude API 대기가 대부분이라 대기형 부하로는 CPU가 안 오른다 — 시연에는 연산형 부하가 필요 (앱의 병목 특성과 스케일링 지표가 맞아야 한다는 교훈)

**Q. 파드가 CreateContainerConfigError면 뭘 보나?**
- `kubectl describe pod`의 Events — 원인이 항상 명시된다. 이미지 풀 성공 이후, 시작 이전의 설정 검증 실패(Secret 누락, securityContext 검증 불가 등)
- 겪은 사례: `runAsNonRoot` + 이름 기반 USER → kubelet이 UID를 판정 못해 거부 → `runAsUser: 1000` 명시

## 4. CI/CD·GitOps 질문

**Q. GitOps가 뭔가, 일반 CI/CD와 뭐가 다른가?**
- **"Git이 배포 상태의 단일 진실 공급원"** — CI는 이미지를 만들고 Git(매니페스트)을 갱신할 뿐, 실제 배포는 클러스터 안의 에이전트(ArgoCD)가 Git을 보고 수행
- 차이: 배포 이력이 곧 Git 이력, 수동 변경(drift)이 자동 복원, 클러스터 자격증명이 밖으로 안 나감

**Q. 이미지 태그 전략은?**
- **태그 = 커밋 SHA, IMMUTABLE** — 코드와 이미지가 1:1 대응, "지금 뜬 파드가 어느 커밋인가"를 항상 답할 수 있다. latest 태그는 재현성이 없어 배제

## 5. 트러블슈팅 스토리 3건 (STAR 압축)

### ① 노드그룹 무증상 실패 — "원인이 기록되는 곳"
- **상황**: 첫 apply에서 노드그룹만 38분간 실패. 상태 API(health.issues)는 끝까지 빈 값
- **행동**: "인스턴스가 떴는가?"로 문제를 이분 → 기동 자체가 거부됨 확인 → 원인이 실제로 적히는 곳(ASG 활동 로그)에서 발견: Free Plan 계정의 인스턴스 타입 제약
- **결과**: 우회(타입 변경) 대신 근본 해결(Paid 전환), 코드 무수정 재성공
- **배운점**: API가 조용하다고 정상이 아니다 — 실패는 기록되는 곳이 따로 있다

### ② OIDC 인증 실패 — "상대가 실제 보낸 값"
- **상황**: CI의 AWS 인증 실패, 에러는 "Not authorized" 한 줄
- **행동**: 가설 2개(전파 지연·정책 연산자)를 세우고 검증으로 기각 → CloudTrail userIdentity에서 GitHub이 실제 제시한 sub 확인 → 신형식(@계정ID·@저장소ID)과 모듈의 구형식 조건 불일치 발견
- **결과**: Role 직접 정의 + ID 고정 — rename 공격 방어라는 보안 부수효과
- **배운점**: 신뢰 정책은 "내 기대"가 아니라 "상대의 실측값"과 일치해야 한다. 추측으로 정책을 고치는 것보다 실측이 압도적으로 빠르다

### ③ 토큰 등록 사고 재발 — "조심이 아니라 절차"
- **상황**: PAT 등록 실패가 형태를 바꿔 2번 발생 (1차 개행 혼입 → 2차 클립보드 덮어쓰기)
- **행동**: 1차 대응(pbpaste)이 2차 사고의 원인이 된 구조를 분석 — 클립보드가 공유 자원이라 실행 순서에 의존
- **결과**: 클립보드를 데이터 경로에서 제거(hidden prompt), 비밀값은 노출 없이 길이·접두사로 진단하는 방법 정립
- **배운점**: 같은 증상 두 번째는 부주의가 아니라 프로세스 결함의 신호

## 6. 운영·비용 질문

**Q. 비용은 얼마나 들었나?**
- 상시 가동 시 월 약 $164 — 그래서 **작업할 때만 apply, 끝나면 destroy**. 하루 종일 리허설한 날 2,000원 미만
- destroy 후엔 terraform state 밖 리소스(컨트롤러가 만든 ALB, PVC의 EBS)까지 **13개 항목 전수검증** — 고아 리소스의 조용한 과금이 제일 무섭다

**Q. 재해가 나면 얼마 만에 복구 가능한가?**
- 문서화된 재기동 루틴(9단계)으로 **20분 내 전체 스택 복원, 5회 실증**. 단 RDS 데이터는 destroy 시 초기화되는 구성(skip_final_snapshot)이라, 실서비스라면 스냅샷·PITR 전략이 선행되어야 함을 인지

## 7. 약점 방어 (꼬리질문 대비)

| 예상 공격 | 답변 태도: 인정 + 이유 + 다음 단계 |
|---|---|
| "테스트 코드가 없네요?" | 맞다. 인프라 검증에 우선순위를 뒀고, CI에 테스트 단계가 없는 것과 연결된 한계로 **백로그에 명시**해뒀다. 앱을 고도화하는 시점에 pytest + CI 테스트 단계부터 추가할 계획 |
| "앱이 너무 단순한데요?" | **의도적 설계** — 평가 대상은 인프라·배포·운영이고, 앱은 그것을 관통하는 최소 검증 단위. 대신 stateless·Secret 주입·프로브·non-root 같은 규약은 전부 지켰다 |
| "고가용성이 안 되네요 (단일 NAT, Single-AZ RDS)?" | 비용 통제를 위해 **인지한 상태로 제외**했고 ADR에 프로덕션 기준(AZ별 NAT, Multi-AZ)을 명시했다. "모르고 안 한 것"과 "알고 뺀 것"은 다르다 |
| "혼자 한 프로젝트라 협업 검증이 안 되는데요?" | repo 분리·PR 가능한 구조·ADR/트러블슈팅 문서화는 **팀에서 일하는 방식을 혼자서도 지킨 것**. 문서들이 곧 협업 인터페이스다 |
| "AI 도구 써서 만든 것 아닌가요?" | 활용했다 — 실무에서도 쓰는 도구고, 중요한 건 **결과를 검증하고 의사결정을 내가 했다는 것**. 모든 트러블슈팅의 진단 과정과 ADR의 트레이드오프 판단을 직접 설명할 수 있다 |
